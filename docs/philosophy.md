# Canopy 철학

> 이 문서의 규칙: **모든 원칙은 "누가 강제하는가"와 "어떻게 점검하는가"를 함께 적는다.**
> 점검 명령이 없는 주장은 원칙이 아니라 희망사항이므로, 이 문서가 아니라
> [second-brain.md](second-brain.md)의 로드맵에 적는다.
>
> 강제 수준 표기 — **[코드]**: 위반이 불가능하거나 명령이 거부함.
> **[검출]**: 위반은 가능하지만 `canopy lint`가 잡아냄. **[협약]**: 코드가 강제하지
> 않는 약속. 협약은 최소화하고, 협약임을 숨기지 않는다.

## 배경: 왜 이 프로젝트인가

이전 시스템(2026-04~06)은 규칙을 900줄짜리 스킬 문서의 산문 체크리스트로 유지했다.
그 문서에는 실패 사례가 계속 append됐다: index 수치 드리프트, git push 누락,
root 파일 생성, 로그 형식 혼동. **문서가 위반 기록으로 비대해지는 것 자체가
"프롬프트로 규칙을 강제할 수 없다"는 증거였다.**

Karpathy의 LLM wiki 철학에서 Memex가 못 풀었던 문제는 "누가 유지보수를 하는가"였고,
그의 답은 LLM이었다. canopy의 답은 한 단계 더 구체적이다:
**판단은 LLM이, 불변식은 코드가.** LLM에게 체크리스트를 외우게 하지 말고,
체크리스트가 필요 없는 도구를 쥐여준다.

## 원칙

### 1. 규칙은 프롬프트가 아니라 코드가 강제한다 **[코드]**

`canopy new`는 잘못된 type·taxonomy 밖 tag·무효 slug·존재하지 않는 `--links`
대상을 **거부**한다. checkin은 사본의 스키마와 base를 검사한다. update는 기존
frontmatter를 유지하고, 본문 위키링크와 외부 편집의 문제는 lint가 검출한다.
모든 명령에 동일한 전체 스키마 게이트가 있다는 뜻은 아니다.

- 점검: `canopy new x --type guide` → 에러. `canopy new x --type concept --tags 없는태그` → 에러.
  `canopy new "제목" --slug link-probe --type concept --links no-such-page --wiki "$W"`
  → `--links target ... does not exist` 오류, 페이지 파일 변경 없음 (`$W`는 스크래치 위키).

### 2. 파생물은 손으로 만지지 않는다 **[코드]**

`index.md`, `index/*.md`, 검색 인덱스 DB(`$XDG_CACHE_HOME/canopy/`)는 재구축 가능한
파생물이다. Markdown 인덱스의 수치는 파일시스템 실측이며
`<!-- generated by canopy -->` 마커가 붙는다. 다음 쓰기는 Markdown 인덱스를
전체 재생성한다. `logs/*.jsonl`은 별개다: canopy가 **append하는 활동 이력**이며
과거 기록을 현재 페이지에서 재생성하지 않는다. 인덱스·로그 모두 직접 편집하지 않는다.

- 점검: `canopy status --json`의 pages 수 == `index.md`의 Total pages ==
  `ls entities concepts comparisons | grep -c '\.md$'` 실측값.
- 점검: `go test ./internal/genindex/ ./internal/logops/` — 인덱스 생성과 JSONL 기록.
  보존 확인은 기존 로그의 바이트를 저장한 뒤 쓰기·reindex 후 그 prefix가 같은지 비교한다.

### 3. 원본과 상태와 캐시를 구분한다 **[코드]**

| 데이터 | 위치 | 성격 |
|---|---|---|
| 지식 (페이지, raw/) | 위키 repo, 커밋 | 원본 — 사람과 LLM의 산출물 |
| 스키마 (canopy.toml) | 위키 repo, 커밋 | 원본 — 데이터의 규칙은 데이터와 함께 여행 |
| 활동 로그 (`logs/*.jsonl`) | 위키 repo, 커밋 | 재현 불가 append-only 이력 — 캐시 삭제·reindex로 복원되지 않음 |
| Markdown 인덱스 (`index.md`, `index/`) | 위키 repo, 커밋 | 전체 재생성 가능한 파생물 |
| 태스크·정규화 원장 (`_meta/tasks/`, `_meta/reconcile/`) | 위키 repo, 커밋 | 재현 불가 위임·검토 상태 |
| resurface 상태 (`_meta/resurface/`) | 위키 repo, 커밋 | **재현 불가** 상태 — 기기 간 동기화 필요 |
| 읽기 이력·검색 갭 (`_meta/webui/`) · 에이전트 접근 집계 (`_meta/attention/`) | 위키 repo, 커밋 | **재현 불가** 상태 — 주의(attention)의 기록도 동기화 필요 (원칙 12) |
| 접근 이벤트 상세 | `$XDG_STATE_HOME/canopy/attention/<해시>.db` | 머신-로컬 상태 — 재현 불가지만 로컬-보강. 동기화되는 진실은 위 `_meta` 집계 (원칙 12, [web-ui-plan-4.md](web-ui-plan-4.md)) |
| 검색 인덱스 | `$XDG_CACHE_HOME/canopy/index/<해시>.db` | 파생 캐시 — 위키 밖, 언제든 재구축 |
| 웹 인증 (`webauth.json`) | `$XDG_CONFIG_HOME/canopy` | 머신 로컬 **비밀** — git으로 여행하면 안 되는 것 |
| 전역 설정 / 모델 | `$XDG_CONFIG_HOME/canopy` / `$XDG_DATA_HOME/canopy` | 머신 로컬 (XDG Base Directory 준수) |

위키 안에는 원본·스키마·Markdown 인덱스·이력·동기화할 상태가 있다.
반대로 비밀(인증)은 어떤 경우에도 위키에 넣지 않는다 — 위키는 공유·복제되는
물건이기 때문이다. 캐시가 위키 밖이므로 gitignore 항목조차 필요 없다.

- 점검: 임시 XDG 캐시의 검색 DB를 지우고 `canopy reindex --wiki <path>` 후 검색한다
  (불변식 C4). 페이지·raw·로그·위키 상태의 해시도 비교한다. 이벤트 DB는 비권위지만
  재현 불가 관측 이력이므로 검색 캐시와 같은 복구를 약속하지 않는다 (불변식 N).
- 점검: `test ! -e <wiki>/.canopy` (위키 안에 캐시 없음). `git -C <wiki> ls-files _meta/` → resurface·webui 추적됨.
- 점검: `git -C <wiki> ls-files | grep -c webauth` == 0 (비밀은 위키 밖).

### 4. 검색이 탐색을 대체한다 (The Wall 해법) **[코드]**

Karpathy가 지적한 "index.md가 수백 페이지를 넘으면 탐색 불가" 문제를 index 계층
확장이 아니라 검색(FTS5 BM25 + bge-m3 벡터, RRF 융합)으로 푼다. index.md는
사람용 대시보드일 뿐, 에이전트의 진입점은 `canopy search`이고 사람의 진입점은
웹 UI의 검색박스다(검색-우선 홈, [web-ui-plan.md](web-ui-plan.md) 참조).
분류가 필요한 곳에서도 트리를 키우지 않고 facet(dir×type×tag 교차 필터)을 쓴다.

- 점검: `canopy search "산업용 프로토콜" --json` — 한국어 시맨틱 매칭 확인.
- 임베딩은 프로세스 내장(ONNX Runtime)이다. 외부 서버가 없으므로 "서버 다운 →
  검색 마비" 실패 모드가 없다. 점검: ORT 빌드·모델·인덱스를 준비한 스크래치 위키에서
  네트워크를 끊고 `canopy search "산업용 프로토콜" --mode semantic --wiki "$W"`.
  준비 조건이 없으면 이 점검은 미검증이다.

### 5. 커밋은 의도적 행위, 잊어버림은 시스템이 막는다 **[코드]**

여러 쓰기를 하나의 커밋으로 묶는 판단은 사용자/에이전트의 것이므로 자동 커밋하지
않는다. 일반 text 명령은 미동기 배너(⚠)를 띄우고 쓰기 뒤 sync를 안내한다.
JSON 모드와 `show`에는 배너가 없으므로 상태 확인이 필요한 절차는 status를 직접 읽는다.
`canopy sync`는 upstream이 있으면 pull을 먼저 수행하고 **기존 dirty 변경까지 전부**
commit/push한다. pull 선행이 충돌이나 push 실패를 없애는 보장은 아니다.

- 점검: 스크래치 위키 파일의 **내용을 수정** → `canopy status --wiki <path>`에서 dirty 확인.
- 점검: `canopy status --json --wiki <path>`의 git·checkouts_open·tasks_pending 확인.
- 점검: upstream이 있는 스크래치 저장소에서 `canopy sync`의 pull 선행 확인 (불변식 D).

### 6. 코드가 후보를 만들고, 사람이나 에이전트가 판단한다 **[코드+협약]**

canopy는 유사도·백링크·날짜·저장된 반응으로 후보를 추린다. 연결의 의미,
모순 여부와 전달할 문장은 사람이나 에이전트가 판단한다. `bridge`와 `resurface hub`의
순위는 입력과 시각 조건을 고정해 비교할 수 있지만, `resurface random/auto`의 표본은
실행마다 달라질 수 있다. `--peek`는 후보를 보여 주되 선정 상태를 기록하지 않는다.

- 점검: `canopy bridge --peek --json` — 임계값 이상·미연결 페어만 나오는지.
- 점검: `go test ./internal/resurface/ -run '^(TestPickHub|TestPickRandomExcludesFreshAndCooldown)$' -count=1` — 고정 입력의 hub 선정과 random의 제외 조건을 확인한다.

### 7. raw/ 는 불변이다 **[협약]**

canopy는 raw/를 절대 쓰지 않지만(코드에 raw/ 쓰기 경로가 없음), 에이전트나 사람이
고치는 것까지 막지는 못한다. 정정은 위키 페이지에서 하고 raw는 그대로 둔다.

- 점검(부분): `git -C <wiki> log --oneline -- raw/ | head` — raw 수정 커밋이 있는지 감사.

### 8. 문서의 모든 주장은 점검 가능해야 한다 **[협약 — 이 문서 자신에 적용]**

이 문서와 [invariants.md](invariants.md)에 점검 명령 없는 주장을 추가하지 않는다.
새 기능은 (1) 불변식을 정하고 (2) 점검 방법을 invariants.md에 먼저 적은 뒤 구현한다.
전체 감사는 invariants.md의 절차로 언제든 수행할 수 있다.

### 9. 문은 여러 개여도 복도는 하나다 **[코드+협약]**

쓰기 인터페이스는 늘어날 수 있다 — CLI, 웹 편집기, 앞으로 무엇이든. 원칙은
"CLI만 쓴다"가 아니라 **모든 변경이 같은 파이프라인(`writeops.Run`: 검증 →
쓰기 → index 재생성 → 로그 → 재인덱싱)을 지난다**는 것이다. 기준은 프로그램
소속이 아니라 파이프라인 동일성이다: canopy 안에 있어도 이 복도를 우회하는
쓰기 코드는 위반이고, 새 인터페이스가 복도를 지나면 원칙은 지켜진 것이다.
웹 편집기는 본문 변경을 제안 태스크로 접수한다. 에이전트가 내용을 검토한 뒤
CLI의 쓰기 파이프라인으로 반영한다. 웹 요청과 파일 변경의 경계는
[agent-tasks.md](agent-tasks.md)에 정리되어 있다.

복도가 하나라는 것과 별개로, **문에는 등급이 있다.** 강제는 두 층이기 때문이다:
명령별 구조 검증·후처리는 canopy 코드가 맡지만, **콘텐츠 판단 규칙**(작성 전 검색,
중복 대신 갱신, 모순은 병기, 진짜 관련만 링크)은 스킬이 안내하는 협약이다.
에이전트가 사용해도 의미적 정확성이 자동으로 증명되지는 않는다.

| 등급 | 경로 | 지켜지는 것 |
|---|---|---|
| **본길** | 사람 또는 LLM 에이전트의 canopy 명령 (에이전트는 스킬 참조) | 명령별 구조 검증 + 작성자의 콘텐츠 판단 |
| 본길 접수구 | 웹 편집·요청 (제안 태스크 접수 → 에이전트 처리, [agent-tasks.md](agent-tasks.md)) | 접수만으로 페이지는 바뀌지 않음; 처리 후 현재 내용을 확인 |
| 뒷길 | Obsidian 등 직접 파일 수정 | 아무것도 — 자가치유와 lint·reconcile 검출에 의존 |

따라서 본격적인 작성·개편은 **본길로 한다** [협약]. 뒷길은 작고 불가피한
수정(오타, 한 줄 정정)에 한한다. 웹 편집은 원래 "직접 저장" 샛길(구조 불변식만
지키는 잠정 설계)이었으나, **2026-08-02 제안 경로로 전환**됐다 — 저장은 edit
태스크 접수이고, 에이전트가 콘텐츠 규칙을 지키며 반영한다 (invariants I2·T).

편집을 막을 순 없다는 전제에서, 이 등급표의 다음 진화는 **정규화(reconcile) 게이트**다:
편집은 어느 문에서든 자유롭게 하되, 그 변경이 main의 진실이 되는 지점(정규화=커밋)은
한 문으로 모아 본길이 재판단한다 — 샛길·뒷길이 우회한 콘텐츠 판단을 정규화 시점에
건다는 운영 협약이다. reconcile은 opt-in 검출이며 sync 자체가 의미 검토를 강제하지는
않는다. 설계·불변식: [reconcile-design.md](reconcile-design.md), invariants K.

- 점검: 웹 편집 저장은 파일을 쓰지 않고 edit 태스크만 접수한다 (invariants I2·T9).
- 점검(협약 감사): pending 태스크가 오래 방치되지 않는지 — `canopy tasks list --json`
  의 `created`가 수 주 전인 항목이 쌓이면 loop가 죽은 것.
- 점검: `go test ./internal/webui/ -run TestWebEditFilesProposalNotFile` — 제안 전문 보존과
  페이지 해시 불변. 웹은 `_meta/`의 큐·읽음·피드백 상태를 기록하지만 페이지 Markdown을
  직접 바꾸지는 않는다. 특정 파일 쓰기 API의 부재만으로 이 경계를 증명하지 않는다.

### 10. 확언과 추측을 구분한다 **[코드]**

위키가 아는 것에는 두 등급이 있다. **확언**: 사람/에이전트가 판단해 심은 명시적
위키링크. **추측**: 임베딩 유사도가 발견한 후보(페이지 하단 제안 링크, bridge
페어, 섬의 다리 제안). canopy는 추측을 확언으로 자동 승격하지 않고 — 링크
삽입은 콘텐츠 판단이므로 원칙 6의 분담을 따른다 — UI에서도 둘을 시각적으로
구분한다(제안은 점선). 추측이 본문 링크와 겹치면 후보에서 제외되므로 같은
연결이 두 등급에 동시에 존재하지 않는다.

- 점검: `canopy bridge --peek --json` → 전부 `linked == false`.
- 점검: 웹 페이지 하단 제안 링크에 그 페이지의 아웃바운드/백링크가 나오지 않는다.

### 11. 외부 바인딩에는 인증이 따른다 **[코드]**

serve의 기본 바인딩은 localhost다. loopback 밖으로 여는 순간 인증 벽이 자동
활성되며, 계정이 없으면 터미널에만 출력되는 1회용 설정 코드 없이는 계정을
만들 수 없다(선점 레이스 차단). 이 보장은 canopy의 listener 바인딩에 적용된다.
localhost backend를 외부 프록시로 공개하면 canopy는 그 노출을 알 수 없으므로
프록시의 인증 또는 canopy의 외부 바인딩 인증을 구성해야 한다. `--allow-host`는
기본 허용 Host에 명시한 authority를 추가하며 인증을 켜는 스위치가 아니다.

- 점검: `canopy serve --addr :8737` 기동 후 무인증 `curl -s -o /dev/null -w '%{http_code}' http://<ip>:8737/` → 302 (내용 없음).
- 점검: `curl localhost:8737` (localhost 바인딩) → 200, 인증 없음 그대로.

### 12. 주의(attention)도 상태다 **[코드]**

무엇을 읽었는가는 재현 불가능한 상태이므로 위키에 커밋되어 동기화된다
(`_meta/webui/reads.json`, `_meta/attention/agent-reads.json`). 주의가 드나드는
문은 둘이라 가정한다 — **웹**(사람)과 **에이전트**(show/recall) — 그리고 기록의
등급 사다리는 명확하다: **명시(✓/다시 읽음)가 1급**, 자동 감지(체류+스크롤)는 보조,
에이전트 소비는 별도 등급으로 **human 등급을 절대 오염시키지 않는다**(recall로
인용됐다고 unread가 꺼지지 않는다). 반대 방향의 보수성도 지킨다: **노출은 읽음이
아니다** — 검색 히트 나열·재발견 카드·관련 제안은 기록하지 않는다. 스쳐간 것을
주의로 오인하지 않는 이 보수성이 추천과 재발견의 품질을 지킨다. 같은 논리로 검색
갭(위키가 답 못한 질의)도 상태로 축적된다.

저장은 2계층이다: 동기화되는 진실은 위키 안의 작은 **집계**(JSON, 일 단위 양자화)이고,
개별 접근 이벤트 전량은 머신-로컬 SQLite(`$XDG_STATE_HOME`)에 남아 리치 UI를
먹인다 — git이 동기화하는 저장소에 바이너리 DB를 넣지 않기 위한 분리다
([web-ui-plan-4.md](web-ui-plan-4.md)).

- 점검: invariants H1–H8.

### 13. 연결성은 도달 가능성까지다 **[검출]**

고아 검사(백링크 0)는 필요조건일 뿐이다. 서로는 링크됐지만 본토(최대 연결
성분)와 끊어진 섬 클러스터는 고아 검사를 전부 통과하면서 지식 그물 밖에
고립된다. lint가 연결 성분 분석으로 섬을 검출하고, 수리는 원칙 10을 따라
다리 후보(섬↔본토 최고 유사도 페어) 제시까지만 한다 — "의도된 섬"인지의
판단은 사람의 것이다.

- 점검: `canopy lint --json | jq '.counts.island // 0'` == 0 (또는 각 섬이 의도된 것인지 확인됨).

### 14. 진화는 사다리로, 파생물은 버린다 **[코드+협약]**

버전이 오르면 온디스크 상태도 바뀐다. 여기서도 원칙 3의 구분(원본/상태/캐시)이
방법을 가른다. **재현 불가 머신-로컬 상태**(전역 설정, 모델·XDG 레이아웃)는
append-only 정수 사다리로 **단계적으로** 이행한다 — 각 단계는 idempotent하고,
새 버전 첫 실행이 startup에서 기록된 지점부터 `Target`까지 간극을 밟아 올라간다.
반대로 **파생 캐시**(검색 인덱스 DB)는 **절대 이행하지 않는다**: 레이아웃이 바뀌면
버전을 올리고 통째로 버린 뒤 재구축하는 것이 올바른 "마이그레이션"이다. 던져버릴
것을 한 단계씩 이행하는 것은 낭비이고, 재구축이 안전하다는 보증(원칙 2·3, 불변식
C4)이 바로 그 낭비를 면제해 준다. 머신-로컬 사다리의 기록이 바이너리보다 새로우면
startup이 거부한다 (J4). 모든 traveling 파일·옛 바이너리에 같은 가드가 있다고
일반화하지 않는다.

git으로 기기 사이를 이동하는 `_meta/*` 파일은 파일 안의 `version`으로 진화한다.
머신-로컬 이행 기록만으로는 다른 기기에서 가져온 옛 위키의 형식을 판단할 수 없기
때문이다. Load는 옛 형식을 관용적으로 읽고, 변경은 기존 필드를 보존하며 추가한다.
구버전 저장으로 새 필드가 사라질 수 있으면 별도 파일에 둔다.

- 점검: `go test ./internal/config/ ./internal/reads/ ./internal/tasks/`의 옛 형식 읽기·필드 보존 테스트.

- 점검: invariants **J 섹션** (J1 세 버전 노출, J2 사다리 조밀·append-only,
  J3 첫 실행 각인·재실행 no-op, J4 다운그레이드 거부, J5 캐시는 사다리 밖).
- 설계와 개발 규칙(언제 rung을 추가하나): [versioning.md](versioning.md),
  [AGENTS.md](../AGENTS.md).

## 비-목표 (하지 않는 것)

- **자동 커밋** — 원칙 5의 이유로. 사용자가 명시적으로 거부한 설계.
- **위키 데이터 형식 발명** — 순수 markdown + frontmatter + wikilink.
  Obsidian이 그대로 열 수 없는 형식은 도입하지 않는다.
- **외부 서비스 의존** — 임베딩·검색·상태 모두 로컬. 네트워크가 필요한 것은
  git push/pull과 모델 최초 다운로드뿐. 웹 UI도 같은 규칙을 따른다:
  하이라이팅은 서버사이드(chroma), mermaid·수식·그래프 라이브러리는 CDN이
  아니라 바이너리에 내장(vendor)되어 오프라인에서 완결된다
  ([web-ui-plan-3.md](web-ui-plan-3.md) D2).
- **TLS 직접 종단** — 전송 암호화는 tailscale·리버스 프록시의 일이다.
  인증(신원)은 canopy가, 암호화(전송)는 네트워크 계층이 맡는다.
