# 정규화(reconcile) 게이트 설계

> 상태: **설계 — 구현 대기.** 이 문서가 불변식과 점검 방법을 먼저 정한다
> ([AGENTS.md](../AGENTS.md) 황금률, [philosophy.md](philosophy.md) 원칙 8).
> 원칙: **정규화는 한 문으로** — [web-ui-write-design.md](web-ui-write-design.md)의
> "LLM 위임 경로" 아이스박스 항목을, 웹뿐 아니라 **모든 문**으로 일반화한 것.

## 1. 문제 — 단일 커밋 게이트가 무판단이다

편집을 막을 순 없다. 사람은 웹으로도, 다른 곳에 clone해서도, Obsidian으로도
고친다. 원칙 9는 이 문들을 등급(본길/샛길/뒷길)으로 인정하되 샛길·뒷길이 **콘텐츠
판단 규칙을 우회한다**는 사실을 *체념하며 문서화*만 했다.

그런데 무엇이 main의 진실이 되는가 = **발행(publish) 지점은 이미 하나다.** 원칙 5가
커밋을 의도적 단일 행위로 만들었고, 그 구현은 `canopy sync` 하나뿐이다. 문제는 그
게이트가 무판단이라는 것:

```
gitops.CommitAll → git add -A → commit → push
```

`git add -A`가 **본길이든 뒷길이든 dirty한 것을 전부 무차별로** main에 올린다.
새는 곳은 "커밋 지점이 여럿"이 아니라 **"하나뿐인 커밋 지점이 콘텐츠를 판단하지
않는다"**이다. 정규화는 이 단일 게이트에 판단을 끼워 넣는다.

## 2. 모델 — 쓰기 평면과 정규화 평면을 나눈다

- **쓰기 평면** — 누구나 어디서든 편집한다(웹·타 클론·Obsidian). *입력*이지 진실이 아니다.
- **정규화 평면** — main에 canonical로 남는 것. 본길(LLM+canopy)의 판단을 거친 것만.

두 평면을 잇는 것이 **정규화 게이트**다. 새 인프라가 아니라 이미 있는 조각의 재조합:

| 필요 | 이미 있는 것 |
|---|---|
| 무엇이 본길을 거쳤나 판별 | `writeops.Run`이 남기는 활동 로그(`logs/*.jsonl`: `action`·`file`·`note`) |
| 후보 생성(결정론) | 의미 유사도(중복 검출)·`lint`(링크·스키마)·git diff |
| 판단·수정 적용 | 에이전트가 `canopy update/new/mv`(= `writeops.Run`) 호출 |
| 동기화되는 상태 | `_meta/`(resurface 상태와 같은 방식) |

### 2.1 변경의 출처 판별 (attribution)

정규화 마커 이후 바뀐 페이지를 세 부류로 나눈다. 판별은 활동 로그로 한다 — 이를
위해 `writeops`가 쓰기 시 **쓴 직후 내용 해시**를 로그에 남기도록 확장한다(작은 추가).

| 부류 | 신호 | 처리 |
|---|---|---|
| **본길** (에이전트 경유) | 현재 내용 해시 == 마지막 쓰기 로그의 해시, `note`가 웹 아님 | 신뢰 (구조·콘텐츠 이미 판단됨) |
| **샛길** (웹 편집) | 로그 해시 일치, `note == "web edit"` | 구조는 신뢰, **콘텐츠 재판단** |
| **뒷길** (raw 편집·타 클론) | 로그 엔트리 없음 / 해시 불일치 | **전면 재판단**(구조+콘텐츠) |

> **왜 해시인가**: "로그 엔트리 존재"만으로는 부족하다 — 본길이 쓴 뒤 Obsidian이 또
> 고쳤으면 로그는 있지만 현재 내용은 파이프라인 산물이 아니다. 마지막 쓰기 해시와
> 현재 해시를 비교하면 정확히 갈린다.

### 2.2 마커

`_meta/reconcile/state.json` (git 추적 — 기기 간 동기화):
- `blessed_sha` — 정규화를 마친 마지막 커밋. `marker..HEAD`의 커밋 변경이 검토 대상.
- `blessed_hashes` — 작업트리에서 검토·축복한 파일별 내용 해시(부분 진행 허용).

`marker == HEAD` 이고 작업트리에 미검토 외부 변경이 없으면 정규화 평면이 깨끗하다.

## 3. 명령 표면

```bash
canopy reconcile --peek --json   # 후보만 (무흔적) — 에이전트 판단 입력
canopy reconcile                 # 미검토 외부 변경이 없으면 마커를 HEAD로 전진
canopy reconcile bless <path>…   # 그 파일 내용을 "검토함·이대로 수용"으로 기록
canopy status / sync             # 미정규화 외부 변경이 있으면 ⚠ 배너로 노출
```

`--peek --json` 출력(결정론, 원칙 6):

```jsonc
{
  "marker": "<sha>",
  "foreign": [{
    "rel_path": "concepts/foo.md",
    "kind": "raw-edit" | "new-file" | "web-edit",
    "dup_candidates": [{ "slug": "bar", "similarity": 0.86 }],  // 임계값 이상만
    "broken_links": ["no-such-page"],
    "schema_issues": ["invalid-tag: 없는태그"]
  }]
}
```

## 4. 에이전트가 후보로 하는 일 (콘텐츠 판단 = LLM)

canopy는 후보를 줄 뿐, 판단은 에이전트가 한다(원칙 6). 각 외부 변경에 대해:

- **중복** (dup_candidates 높음) → 새 페이지 대신 기존 페이지 **갱신**으로 유도.
- **모순** (기존 내용과 충돌) → 조용히 덮지 말고 **날짜·출처와 병기**.
- **끊긴 링크·스키마 위반** → 수정.
- **문제 없음** → `canopy reconcile bless`로 이대로 수용.

수정은 언제나 `canopy update/new/mv`(= `writeops.Run`)로 한다 — 그래야 로그·인덱스·
임베딩이 따라오고, 그 변경은 다시 "본길"로 기록된다(한 복도, 원칙 9). 검토가 끝나면
`canopy reconcile`이 마커를 전진시키고 게이트가 깨끗해진다. 이 판단은 주기 실행
(기존 lint cron 곁)으로 자동화할 수 있다.

## 5. 정직하게 — "타 클론이 main에 직접 push"

위키는 GitHub 저장소라 서버 훅으로 push를 막을 수 없다. 그래서 이 문은 본질적으로
**예방이 아니라 [검출]+정규화**다(뒷길에 대한 철학의 기존 입장 그대로). `reconcile`이
작업트리뿐 아니라 `marker..HEAD`의 **커밋된 변경도** 검토 대상에 넣으므로, 타 클론이
main에 올린 뒤 pull해도 다음 정규화가 그 diff를 재판단한다. 관례로 "타 클론은 main이
아니라 `proposals/*`로 push"를 권하고, 직접-main 외부 커밋은 lint가 표시한다. main을
push하는 유일한 경로가 정규화 게이트라는 것 — 그것이 "한군데서 관리"의 실체다.

## 6. 불변식 (invariants.md **K 섹션**에 등재)

- **K1** 정규화 마커는 위키에 커밋되는 상태다(기기 간 동기화). `_meta/reconcile/state.json`.
- **K2** 파이프라인 로그가 커버하지 않는 페이지 변경(뒷길)은 후보로 검출된다.
- **K3** 후보는 결정론적이다(원칙 6) — 같은 상태에서 `--peek` 반복 시 동일, dup은 임계값 이상만.
- **K4** `bless`/정규화는 마커를 전진시켜, 검토한 변경은 다시 후보로 뜨지 않는다.
- **K5** `--peek`은 흔적을 남기지 않는다(E6와 같은 규율).
- **K6** 미정규화 외부 변경은 `sync`/`status` 배너로 노출된다(원칙 5·2).
- **K7** 정규화의 콘텐츠 수정은 `writeops` 경유다(한 복도, 원칙 9) **[협약]**.

## 7. 비-목표 / 한계 (정직하게)

- **예방 아님.** GitHub main으로의 직접 push는 막지 못한다 — [검출]+사후 정규화다.
  나쁜 콘텐츠가 잠깐 main에 존재할 수 있다(자가 치유 전제, 원칙 2).
- **자동 병합 없음.** 모순·중복의 해소는 LLM 판단이다. canopy는 후보만.
- **동일 파일 동시 편집**(본길+뒷길)은 해시 불일치로 "뒷길"로 분류되어 재판단된다 —
  보수적으로 안전한 쪽.

## 8. 이 게이트의 자리 (단계론)

이건 **가벼운 정규화 게이트**(사후·비차단)다. 같은 원칙 위에 더 강한 층을 얹을 수 있다:
웹 문을 제안 경로로 전환(웹 편집 → 초안 → 에이전트 처리), 나아가 main을 pristine으로
두고 모든 문을 staging으로 모으는 완전 제안-플레인. 셋 다 **"정규화는 한 문으로"**의
같은 원칙을 강도만 달리 구현한 것이다 — 지금은 가장 가벼운 층부터 놓는다.
