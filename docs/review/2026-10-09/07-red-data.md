# 데이터·상태 감사에 대한 독립 반대심사 — Group A

대상은 Canopy v0.10.0 소스 `ede67e302a8487aecbb4d59587a8686292018cf6`이다. [01-data.md](01-data.md)와 [04-state.md](04-state.md), 각 보고서가 보존한 소스·출력·명령 증거를 심사했다. 먼저 `AGENTS.md`, 원래 `docs/philosophy.md`, `docs/invariants.md`, `docs/versioning.md`를 읽었으며 checkout·agent-tasks 설계를 대조했다. 다른 반대심사자의 출력은 읽지 않았고 하위 작업자를 만들지 않았다. 기존 구현·문서·보고서에는 손대지 않았다.

핵심 손실 주장을 뒤집지는 못했다. 정상 CLI의 겹친 create/update, 정상 웹 접수, archive 이름 재사용, 메타가 손상된 checkout, 쓰기 중 오류, Git autostash 충돌 발행은 독립 fixture에서도 성립했다. 그러나 **활동 로그를 복원 원장으로 바꾸는 제안, 모든 상태의 자동 참조 이관, 의미적 done 검증 강화, 경로 정체성 변경은 이 증거만으로 필수 수정이 되지 않는다.** 단순 index 후처리 실패는 새 본문이 위키에 남는 경우와 구별해야 한다. 버그를 인정한 항목에서도 원자적 rename·Save 잠금·UUID·새 version 하나가 각각 모든 문제를 해결한다는 결론은 거부한다.

## 독립 실행과 반례

실행 환경은 Darwin arm64, Go `go1.27.1`, cgo 없는 lite 빌드다. 기준 디렉터리는 `/private/tmp/canopy-audit-20261009/red_data-ctx206f`이며 CLI 두 번째/최종 실행은 각각 새 하위 root를 만들었다. 원 보고서 fixture나 원 실행 소스를 재사용하지 않았다. 실제 서버를 시작하지 않았으며 HTTP는 제품의 `NewServer().Handler()`와 `httptest`로 수행했다. Git commit/push/pull은 아래 자체 local bare origin·clone만 사용했다.

모든 Go·gofmt·canopy 프로세스에는 임시 HOME/XDG/TMPDIR, `GOCACHE=/private/tmp/canopy-review/go-cache`, `GOPROXY=off`, `GOSUMDB=off`, `GOTELEMETRY=off`, `GOENV=off`, `GOTOOLCHAIN=local`을 설정했다. 기존 `/Users/nobocop/go/pkg/mod`는 명시적인 읽기용 module 입력이고 빌드·테스트에는 `-mod=readonly`를 썼다. 실제 위키·canopy HOME/XDG 상태와 설치된 native/model 자산을 읽거나 쓰지 않았다. 초기 저장소 `git status`/`rev-parse`, 스킬 안내 읽기, Orca 제어 명령과 Python 부모 런처는 세션의 HOME에서 실행했다. 따라서 Go·canopy 격리에 관한 확인을 Orca 등 모든 도구의 사용자 HOME 쓰기가 0이었다는 포괄적 주장으로 확대하지 않는다. 사용자 상태를 정리하거나 변경하지 않았다.

실제로 실행한 명령은 다음과 같다. driver는 자식 환경과 stdout/stderr/exit을 보존한다.

```sh
python3 review_probes/red_data/driver.py build
python3 review_probes/red_data/driver.py existing
python3 review_probes/red_data/driver.py cli
python3 review_probes/red_data/driver.py go
python3 review_probes/red_data/driver.py extra
python3 review_probes/red_data/driver.py goextra
```

빌드의 실제 명령은 `go build -mod=readonly -o /private/tmp/canopy-audit-20261009/red_data-ctx206f/canopy-lite ./cmd/canopy`다. 기존 검증은 `go test -mod=readonly -count=1 -v ./internal/... ./cmd/canopy`이고 exit 0이었다. 자체 Go 관측은 `go test -mod=readonly -count=1 -v ./review_probes/red_data`, 추가 관측은 같은 명령에 `-run '^TestQ1[12]'`를 붙였으며 모두 exit 0이었다. 자체 관측 PASS는 fixture 실행이 끝났다는 뜻이고, 구현의 정상 보증 통과가 아니다. 초기 Python 런처의 inputs 디렉터리 누락과 기존 canopy.toml에 대한 init 전제 오류를 고친 뒤 최종 CLI 전체를 새 fixture에서 완료했다. connect 반례도 **정렬된 페어**로 다시 구성했고, 정렬 때문에 충돌하지 않는 페어를 별도 대조군으로 남겼다.

## 원 증거와 수용 시험의 한계

원 보고서가 지목한 `write.go`, `checkout.go`, `reads.go`, `tasks.go`, `events.go`, `state.go`, `reconcile.go`, YAML helper, CLI/HTTP caller의 행과 호출 순서를 대상 HEAD에서 확인했다. DATA 보고서의 CLI 보존 소스·최종 JSONL·transcript와 Go 관측, STATE의 20 case 소스/최종 출력/runner를 읽어 실제 관측과 조건이 연결되는지도 확인했다. 내부 State Load/Save interleaving·고정-time ID·synthetic future DB를 실 CLI/실제 미래 release의 데이터 손상으로 바꿔 읽지 않았다.

기존 테스트의 통과도 독립 확인했다. `TestCheckinBaseConflict`는 Checkin 호출 **이전** wiki 변경, `TestCheckoutIdempotent`는 정상 meta, `TestRenameMovesAgent`는 메서드, `TestUnknownTypeMixedVersionSafety`는 unknown 문자열 보존·unknown type done 거부, `TestGCNeverRemovesPending`는 identity가 정상인 현재 status fixture다. 이 테스트들은 각각 Q04/P09/P14/P23/P18의 반례를 넣지 않는다. `TestWebEditFilesProposalNotFile`은 전문/POST 시점 base·원문 불변을 검증하며 GET origin이나 동시 N개 보존을 검증하지 않는다. genindex·YAML 기존 테스트는 CLI sync 호출 여부·block scalar 값 교체까지 증명하지 않는다. `gitops`, `writeops`, `indexer`, `cmd/canopy`에는 기존 test file이 없었다.

STATE 보고서의 `TestStateWriteFailureKeepsOldFile` 등 신규 수용 이름은 **제안**이다. 이번 실행 결과의 기존 테스트가 그 이름을 통과했다고 쓰면 안 된다. future 구현에서도 `go test -list`로 실제 테스트 존재를 확인하고 barrier/fault/독립 process의 입력을 확인해야 한다. 단순 `-run` exit 0, 전체 green, Go `-race`로 파일 snapshot 보존을 대체할 수 없다. 이번 심사는 `-race`, ORT, 모델 다운로드, 실제 네트워크/인증, power loss, Windows, ACL/hardlink/symlink write semantics, 전체 fixture 두-clone edit/task 의미 병합, 모든 time/DST 경계, 모든 Record/Log/DB fault 조합은 실행하지 않았다. 실제 user wiki나 오랜 운용의 발생 빈도도 측정하지 않았다.

따라서 기존 심각도 중 연결 의도 ID 충돌을 본문 유실 P1로, 명시 GC·done 의미·seed/경로 선택을 일반 데이터 버그 P2로 유지할 근거는 부족하다. 반대로 성공 응답 뒤 전문 유실이나 unreadable meta의 실패 응답 뒤 copy 손실은 정상 동작 테스트로 반박되지 않는다. 위키 밖 임의 삭제/공격 가능성, 성능 저하, 임베딩 추천 품질 저하는 이번 증거에서 확인되지 않아 결론으로 채택하지 않았다.
