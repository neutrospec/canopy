# 정규화(reconcile) 게이트 설계 — 단일 내용-해시 원장

> 상태: **구현 완료** (2026-07-29) — 불변식 K1–K7 전부 e2e 검증.
> 원칙: **정규화는 한 문으로** — [web-ui-write-design.md](web-ui-write-design.md)의
> "LLM 위임 경로" 아이스박스 항목을, 웹뿐 아니라 **모든 문**으로 일반화한 것.
> 불변식·점검: [invariants.md](invariants.md) **K 섹션**.

## 1. 문제 — 단일 커밋 게이트가 무판단이다

편집을 막을 순 없다. 사람은 웹으로도, 다른 곳에 clone해서도, Obsidian으로도
고친다. 원칙 9는 이 문들을 등급(본길/샛길/뒷길)으로 인정하되 샛길·뒷길이 **콘텐츠
판단 규칙을 우회한다**는 사실을 *체념하며 문서화*만 했다.

그런데 무엇이 main의 진실이 되는가 = **발행(publish) 지점은 이미 하나다.** 원칙 5가
커밋을 의도적 단일 행위로 만들었고, 그 구현은 `canopy sync` 하나뿐이다. 문제는 그
게이트가 무판단이라는 것:

```
gitops.CommitAll → git add -A → commit → push
```

`git add -A`가 **본길이든 뒷길이든 dirty한 것을 전부 무차별로** main에 올린다.
새는 곳은 "커밋 지점이 여럿"이 아니라 **"하나뿐인 커밋 지점이 콘텐츠를 판단하지
않는다"**이다. 정규화는 이 단일 게이트에 판단을 끼워 넣는다.

## 2. 모델 — 축복된 내용의 원장(ledger) 하나

"판단을 거쳤다"의 진실 소스는 커밋 이력이 아니라 **파일별 내용 해시의 원장**이다:

```jsonc
// _meta/reconcile/state.json  (git 추적 — 기기 간 동기화, 자체 version 필드)
{
  "version": 1,
  "blessed": {
    "concepts/foo.md": "<sha256 of file bytes>",
    "concepts/bar.md": "<sha256>"
  }
}
```

**한 문장 정의**: *어떤 페이지의 현재 내용 해시가 원장과 일치하면 그 내용은 판단을
거친 것이고, 아니면 외부(foreign) 변경이다.*

원장에 해시가 실리는 길은 둘뿐이고, 둘 다 "판단"이다:

| 길 | 언제 | 의미 |
|---|---|---|
| **자동** — 파이프라인 쓰기 | `writeops.Run`이 쓴 직후, 쓴 파일들의 해시를 기록 | 본길(에이전트)·샛길(웹 편집)은 파이프라인 산물 — 검증을 거쳤으므로 자동 축복 |
| **수동** — `reconcile bless` | 사람/에이전트가 외부 변경을 검토한 뒤 | 뒷길 산물이지만 "검토했고 이대로 수용" |

이러면 검출은 순수 대조가 된다:

- 파일 있음 + 해시 ∉ 원장 → **foreign** (`edited`: 원장에 옛 해시 있음 / `new`: 항목 없음)
- 원장에 있음 + 파일 없음 → **foreign** (`deleted` — 뒷길 삭제)
- 해시 == 원장 → 이미 판단됨, 침묵

### 왜 커밋 이력이 기준이 아닌가

1. **`sync`가 `git add -A`로 커밋을 뭉갠다** — 한 커밋에 본길·뒷길 수정이 섞이므로
   커밋 단위 축복은 불가능하다. 그래서 bless 단위는 **파일(페이지)**이다.
2. **아직 커밋 안 된 변경**(Obsidian이 방금 고침)은 이력에 없지만 배너는 커밋 전에
   경고해야 한다(K6).
3. 원장 대조는 **상태를 판단하지 이력을 판단하지 않는다** — 되돌림·병합 등 어떤
   경로를 거쳤든 최종 내용이 축복된 것과 같으면 조용하다. 타 클론이 main에 push한
   커밋도 pull 후 파일 내용이 원장과 다르면 자동으로 후보가 된다 — 마커도, 커밋
   추적도 필요 없다. (git 이력은 후보의 diff를 보여주는 데나 쓰는 참고 자료다.)

### 파이프라인의 의무 — Effects 선언

자동 축복이 성립하려면 **파일을 바꾸는 모든 파이프라인 경로가 자기가 쓴 것을
선언**해야 한다. `writeops.Run`이 `Effects{Written, Removed}`를 받아 원장에
반영한다: `mv`는 개명된 파일 + 인바운드 링크를 재작성한 페이지들, `rm --force`·
`archive`는 삭제/이동된 파일(원장에서 제거) + 링크를 걷어낸 페이지들. 한 복도
(원칙 9)가 이미 "모든 변이는 writeops를 지난다"를 보장하므로, 이 선언이 곧
완전성이다.

### 게이트는 opt-in이다

원장이 없는 위키(미초기화)에서는 자동 기록도 배너도 침묵한다 — 기존 위키가
갑자기 "전 페이지 미검토" 소음을 맞지 않게. `canopy reconcile bless --all`이
현재 상태 전체를 기준선으로 축복하며 게이트를 켠다(마이그레이션 사다리의
신규-설치 기준선과 같은 사고방식).

## 3. 명령 표면

```bash
canopy reconcile [--json]          # 보고 (읽기 전용, 무흔적): foreign 후보 나열
canopy reconcile bless <page|path>…  # 그 파일의 현재 내용(부재 포함)을 "검토함"으로 기록
canopy reconcile bless --all       # 현재 상태 전체를 기준선으로 (초기화 겸 일괄 수용)
canopy status / sync               # 미정규화 외부 변경이 있으면 ⚠ 배너로 노출
```

`bless <path>`의 인자는 slug 또는 rel path. 파일이 없는데 원장에 있으면 삭제를
수용한다(항목 제거) — bless는 언제나 "*현재 상태*(부재 포함)를 검토했다"이다.

보고 출력(`--json`, 결정론 — 원칙 6):

```jsonc
{
  "initialized": true,
  "foreign": [{
    "rel_path": "concepts/foo.md",
    "kind": "edited" | "new" | "deleted",
    "dup_candidates": [{ "slug": "bar", "similarity": 0.86 }],  // ≥0.8, 최대 3
    "issues": ["broken-link: [[no-such-page]]", "invalid-tag: 없는태그"]
  }]
}
```

dup 후보는 임베딩 인덱스가 있을 때만 채워진다(검색과 같은 우아한 강등).

## 4. 에이전트가 후보로 하는 일 (콘텐츠 판단 = LLM)

canopy는 후보를 줄 뿐, 판단은 에이전트가 한다(원칙 6). 각 foreign 변경에 대해:

- **중복** (dup_candidates 높음) → 새 페이지 대신 기존 페이지 **갱신**으로 통합.
- **모순** (기존 내용과 충돌) → 조용히 덮지 말고 **날짜·출처와 병기**.
- **끊긴 링크·스키마 위반** (issues) → 수정.
- **문제 없음** → `canopy reconcile bless`로 이대로 수용.

수정은 언제나 `canopy update/new/mv`(= `writeops.Run`)로 한다 — 그래야 로그·인덱스·
임베딩이 따라오고, 그 결과가 자동 축복된다(한 복도, 원칙 9). 이 검토 루프는 주기
실행(기존 lint cron 곁)으로 자동화할 수 있다.

## 5. 비-목표 / 한계 (정직하게)

- **예방 아님.** GitHub main으로의 직접 push는 서버 훅으로 막을 수 없다 — 이 문은
  본질적으로 [검출]+사후 정규화다(뒷길에 대한 철학의 기존 입장 그대로). 나쁜
  콘텐츠가 잠깐 main에 존재할 수 있다(자가 치유 전제, 원칙 2).
- **자동 병합 없음.** 모순·중복의 해소는 LLM 판단이다. canopy는 후보만.
- **본길+뒷길이 같은 파일을 잇달아 고치면** 마지막 내용이 원장과 달라 foreign으로
  뜬다 — 파이프라인 산물까지 재검토하게 되는 보수적으로 안전한 쪽.
- **원장 충돌**: 두 기기가 동시에 bless하면 state.json이 git 충돌할 수 있다 —
  reads.json과 같은 수용 범위(단일 사용자, 드묾).

## 6. 이 게이트의 자리 (단계론)

이건 **가벼운 정규화 게이트**(사후·비차단)다. 같은 원칙 위에 더 강한 층을 얹을 수
있다: 웹 문을 제안 경로로 전환(웹 편집 → 초안 → 에이전트 처리) — **구현됨
(2026-08-02, [agent-tasks.md](agent-tasks.md)의 태스크 큐: 웹 편집·요청이 edit/connect
태스크로 접수되고 에이전트가 처리)** — 나아가 main을 pristine으로 두고 모든 문을
staging으로 모으는 완전 제안-플레인. 셋 다 **"정규화는 한 문으로"**의 같은 원칙을
강도만 달리 구현한 것이다.
