## 판정 기준과 독립 실행 범위

`accept`는 주장한 동작·계약 위반이 증거로 성립함, `narrow`는 더 작은 범위·전제에서만 성립함, `reject`는 실행 버그 또는 의무로 주장할 근거가 부족함, `defer`는 판정에 필요한 실행·제품 결정이 남음이다. **결함 판정과 해결안 판정은 별개**다. `reject`는 관측된 동작 자체를 부인한다는 뜻이 아니라, 그 동작을 결함으로 부르는 논거를 거부하는 경우도 포함한다. 심각도는 원본 P1/P2를 다른 프로젝트의 보안 등급으로 옮기지 않고, 이 로컬 위키에서 현재 근거가 잘못 전달되는지·정상 작업이 막히는지·어떤 복구 길이 남는지로 정했다.

AGENTS.md와 원래 philosophy/invariants/versioning을 먼저 읽었다. 판단은 LLM이 하고 코드는 구조·원문·상태의 불변식을 지킨다는 원칙을 적용했다. **근접 후보를 반환하는 검색에 정답 판정·abstention을 강제로 넣는 것은 원칙 6의 요구가 아니다.** 반면 G2의 원문 보존은 명시 계약이고, “후보이므로 과거 내용을 써도 된다”는 방어는 성립하지 않는다. 캐시 변경은 cache schema로 재구축하며 migration ladder로 옮길 일이 아니다. 새 제안은 이번에 invariants에 등록하거나 구현하지 않았다.

독립 fixture는 `/private/tmp/canopy-audit-20261009/red_search-cc5n2zwb`와 `red_search-x75u1a2t`에 새로 만들었다. 원래 search/ops fixture나 binary를 재사용하지 않았다. 모든 Go·canopy subprocess의 `HOME`, `XDG_CONFIG_HOME`, `XDG_CACHE_HOME`, `XDG_DATA_HOME`, `XDG_STATE_HOME`, `TMPDIR`를 해당 임시 영역으로 지정했고, `GOCACHE=/private/tmp/canopy-review/go-cache`, `GOPROXY=off`, `GOTELEMETRY=off`, `GOTOOLCHAIN=local`, `CGO_ENABLED=0`를 사용했다. 읽기 전용 의존성 재사용 경로는 명시적으로 `/Users/nobocop/go/pkg/mod`이다. 실제 사용자 위키·canopy HOME/XDG·설치 모델·native 라이브러리는 열지 않았으며 다운로드·양자화·서비스·commit/push/release를 하지 않았다. Go SDK는 `go1.27.1 darwin/arm64`로, 선언된 Go 1.26.4와 동일 툴체인 검증은 아니다.

처음의 skill/CLI guide 읽기와 Git HEAD/status 조회는 기존 shell 환경에서 했다. **Go나 canopy를 기존 HOME으로 실행한 적은 없다.** 다만 `GOTELEMETRY=off`를 지정한 독립 test에서도 SDK counter 파일이 *임시* HOME 안에 생겼다. 따라서 “환경변수만으로 도구가 HOME에 전혀 쓰지 않는다”는 주장은 하지 않으며, 이 파일과 canopy 이벤트 DB를 구분했다. 원본 search 실행기는 `go env GOMODCACHE`를 격리 env 구성 전에 호출하고 TMPDIR/GOTELEMETRY도 고정하지 않는다. 원본의 “실제 HOME 수정 없음”을 도구 전체의 무쓰기 증명으로 확대할 수 없다. ops 원본은 이 한계를 이미 명시했다. 실제 HOME의 확인·청소·되돌리기는 하지 않았다.

## RED-B-01 — make deps가 curl 실패 status를 잃고 다음 시도도 생략함

**새 관측·아직 방어되지 않음. 결함 잠정 narrow / 해결안 잠정 narrow / 낮음.** 원본 OPS-08의 “digest·완료 검증 없음”과 연관되지만, 원본이 실행하지 않았던 **실패 exit 전달**을 별도 ID로 남긴다.

독립 fake curl은 완전한 toy gzip tar를 stdout에 쓴 뒤 **exit 7**을 반환했다. Makefile:57의 `curl ... | tar xz ...`에서 tar가 exit 0이면 make도 exit 0이었다. toy `libtokenizers.a`가 37B 생성되었으며 다음 `make -n deps`는 `Nothing to be done`이었다. 가짜 실행기는 fixture PATH 앞에만 두었고 실제 HTTP·정상 native lib에 접근하지 않았다. argv·fixture 생성·출력은 추가 실행기 및 `make-failed-curl-toy`, `toy-lib-result`, `make-next-attempt` 기록에 있다.

가장 강한 반론은 curl이 오류라도 받은 archive가 완전하고 digest까지 맞으면 유효 artifact일 수 있다는 것이다. 맞다. 이번 toy는 transfer exit를 무시한다는 코드 경계만 증명하며 **실제 upstream이 잘못된 library를 줬거나 native install이 손상됐다는 증거는 아니다**. 다만 현재는 digest 단계도 없으므로 tar 성공/파일 존재를 download success와 동일시한다.

최소 해결 검토는 원본 OPS-08의 임시 검증 범위 안에서 curl을 임시 archive 파일로 받고 실패 status를 검사한 뒤 digest·추출·교체하는 것이다. 플랫폼 `/bin/sh`에 무조건 `set -o pipefail`을 추가하는 해법은 이식성 문제가 있으며, 실패한 staging이 기존 정상 lib를 지워서는 안 된다. 인수 조건은 fake transfer error와 hash mismatch가 readiness를 만들지 않고 old artifact를 보존하며 재시도가 다시 검증하는 것, 또는 **정확한 digest 검증을 통과한 artifact라면 transfer 오류를 허용한다는 명시 정책**이다. 방어 질문은 “프로젝트의 성공 기준은 transport status인가 verified artifact인가, 그리고 현재 그 둘을 구분하는 검사 위치가 있는가?”다.
