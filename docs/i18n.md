# 다국어 문서(i18n) 관리

> 상태: 방법론 확정 · 도구 구현. 원칙: **소스는 하나, 번역은 파생 — 그리고 파생의
> 낡음은 점검 가능해야 한다**([philosophy.md](philosophy.md) 원칙 8).
> 불변식·점검: [invariants.md](invariants.md) **L 섹션**.

## 무엇을 · 왜

README와 사용자 문서를 한국어(소스)·영어(번역)로 제공한다. 설계 기록(philosophy,
invariants, versioning, reconcile-design, web-ui-plan-* 등)은 내부 개발 문서라
번역하지 않는다 — 소스(한국어)만 둔다.

핵심 난제는 구조가 아니라 **번역 지연(staleness)**이다: 소스가 바뀌면 번역은 조용히
낡는다. 이 프로젝트는 "문서가 현실과 어긋나는 것"을 병으로 보므로(원칙 8), 번역이
낡았는지도 **검출 가능**해야 한다 — 방금 만든 [reconcile 게이트](reconcile-design.md)와
구조가 똑같다: 한국어=소스(원장), 영어=파생, 소스 해시가 바뀌면 번역은 "낡음"으로
뜨고 재번역이 필요하다. 번역·재동기화는 에이전트가 한다("판단은 LLM이").

## 구조

| | 소스 (한국어) | 번역 (영어) |
|---|---|---|
| README | `README.md` (루트) | `README.en.md` (루트) |
| 사용자 문서 | `docs/*.md` | `docs/en/*.md` (같은 파일명 미러) |

- 한국어를 **현 경로에 그대로** 둔다 → 코드의 `docs/*.md` 참조도, 문서 간 상대 링크도
  안 깨진다. 영어는 미러 서브트리(`docs/en/`)에서 자기들끼리 링크한다.
- 언어 스위처: 각 문서 최상단 한 줄. 한국어 `> **한국어** · [English](…)`,
  영어 `> [한국어](…) · **English**`. 양방향으로 서로를 가리킨다.

## 번역 파일의 두 표식

각 번역 파일 **1행**에 보이지 않는 소스 마커(HTML 주석 — GitHub에서 렌더 안 됨):

```
<!-- i18n-source: docs/getting-started.md sha:<git blob sha> -->
```

- `<path>` = 소스 파일(레포 루트 기준). `<sha>` = 번역 시점 `git hash-object <path>`의
  전체 40자.
- 소스가 바뀌면 그 sha가 달라진다 → 번역이 낡았다는 신호(L2가 STALE로 검출).
- YAML front-matter 대신 HTML 주석을 쓰는 이유: GitHub은 `.md`의 `---` front-matter를
  **표로 렌더**해 지저분하다. 주석은 안 보이고 grep·diff는 된다.

## 점검 (invariants L)

```bash
make i18n-check      # scripts/i18n-check.sh — CI(ci.yml)에 포함
```

- **L1** 모든 번역이 소스 마커를 갖는다 (없으면 MISSING).
- **L2** 기록 sha == 현재 `git hash-object <source>` (다르면 STALE) — 재번역 신호.
- **L3** 코드·명령·경로는 번역하지 않는다 **[협약]** — 부분 점검으로 소스·번역의
  코드펜스(```) 개수 일치를 본다(FENCE MISMATCH). 점검 명령이 언어 간 갈리면 안 되기
  때문이다 — invariants.md의 셸 명령이 그 예다.

낡은 번역은 CI를 빨강으로 만든다 → **소스를 고친 변경에서 번역도 함께 갱신**하는 게
규율이다([AGENTS.md](../AGENTS.md)). 소스 변경과 번역을 lockstep으로 두는 것이 목적이라,
검출을 예방이 아니라 lockstep 압력으로 쓴다.

## 번역 절차 (에이전트)

1. 소스(한국어)를 최종 상태로 둔다.
2. `docs/en/<같은이름>.md`(또는 `README.en.md`)에 번역. **코드펜스 안은 손대지 않는다** —
   셸 명령·경로·식별자·출력·플래그는 그대로. 산문만 번역한다.
3. 1행에 소스 마커를 `sha:$(git hash-object <source>)`로 기록.
4. 최상단에 스위처 줄. 소스 문서에도 반대 방향 스위처 줄(양방향 링크).
5. `make i18n-check` 초록 확인.

## 지금 하지 않는 것

- **설계 기록 번역** — 내부 개발 문서라 소스(한국어)만. 필요해지면 같은 방식으로 확장.
- **문서 사이트(i18n UI)** — 지금은 GitHub 렌더 마크다운으로 충분. Docusaurus/VitePress
  류는 규모가 커지면 재고한다(그때도 이 소스 마커·점검은 그대로 유효하다).
- **번역을 원본인 척** — 영어는 언제나 한국어의 파생이다. 두 언어를 각각 손대 갈라지게
  하지 않는다(원칙: 소스는 하나).
